Distributed Compute Cluster

An experimental over-the-Internet distributed compute cluster that coordinates multiple devices (iPhones, Macs, and other SSH-reachable nodes) over SSH across either a local network or a VPN mesh. Workloads are split across nodes, processed in parallel, and returned through a length-prefixed TCP protocol for deterministic aggregation.

Adaptive Optimization (The Key Innovation)

  • The Network Bottleneck: Internet routing introduces erratic ping latencies that can paralyze traditional parallel cluster configurations.
  • Dynamic Packet Tuning: An automated network ping test executes right before data distribution.
  • Healthy links: Use responsive 256 KB packet chunks.
  • Moderate or cautious links: Use 1 MB or 2 MB chunks based on latency and jitter.
  • Unstable links: Abort above 150 ms average latency or 2% packet loss.

< 30 ms< 10 ms0%Proceed with 256 KB chunks
30–80 ms10–40 ms0%Proceed with 1 MB chunks
80–150 ms> 40 ms< 1%Proceed cautiously with 2 MB chunks
> 150 msAnyAnyAbort and re-profile after fixing the link
AnyAny> 2%Abort because the link is unstable

Classification uses the worst observed condition. Packet loss from 1–2% does not satisfy a proceed tier and aborts conservatively. A rejected worker stops the run before any compute process is launched.

Technical Execution Workflow

  • Deployment: deploy_cluster.sh uses parallel background tasks to sync code, detect operating systems (iSH Alpine vs Native iOS), and configure dependencies automatically.
  • Profiling: run_cluster.sh benchmarks connection latencies and starts remote background worker ranks over SSH.
  • Calculation: Workers stream data chunks, process heavy dot-product row loops inside their hardware memory pools, and return calculations.
  • Verification: The master node aggregates chunks, renders progress bars, saves a final unified .csv report, and engages mathematical delta checkers.

Key Findings & Performance Scaling

  • Compute vs. Network Cost: iPhone hardware handles local matrix multiplication instantly, but internet bandwidth limits linear speedup scaling.
  • Amdahl's Law in Action: The project illustrates how a slower communication layer introduces parallel overhead, demonstrating real-world high-performance computing (HPC) constraints.

Quick Start

Prerequisites

  • WireGuard for nodes that are not on the same local network as the orchestrator.
  • SSH key-based auth configured (see SSH hardening guide).
  • Python 3 + numpy on all matrix-compute nodes.
  • macOS worker nodes should have either Python 3 preinstalled or Homebrew available so deploy_cluster.sh can install it automatically.

run_cluster.sh is local-network aware for IPv4 ranges that start with 192.*, 10.*, or 172.* (project first-octet rule, including all 172.*). If a worker is on the same local network family as the host, it uses the host LAN IP and does not require VPN host configuration. For mixed LAN-local and VPN-only workers in one run, set ALLOW_MASTER_WILDCARD_BIND=1 so rank 0 can bind on 0.0.0.0.

1. Deploy dependencies to worker nodes

bash deploy_cluster.sh

2. Run the cluster

bash run_cluster.sh

3. View the report

cat FINAL_PROJECT_SUMMARY.md

Local Docker smoke test

bash docker/setup_keys.sh
docker compose -f docker/docker-compose.yml up --build -d
docker compose -f docker/docker-compose.yml exec master bash deploy_cluster.sh
docker compose -f docker/docker-compose.yml exec -e MATRIX_SIZE=32 master bash run_cluster.sh
docker compose -f docker/docker-compose.yml down

Latest verified result: two healthy worker links selected 256 KB chunks, the distributed 32×32 workload completed successfully, and numerical verification passed with a maximum delta of 4.99929e-05.

For detailed step-by-step commands including smoke tests and troubleshooting, see the browser-friendly run guide.

Executable LLM Pipeline

run_llm_cluster.sh launches MLX-LM pipeline-parallel inference locally or across Apple Silicon Macs using MLX ring or JACCL communication.

Compute-node requirement: LLM pipeline ranks must be Apple Silicon Macs. iPhones running iSH remain supported by the separate NumPy matrix workflow, but cannot serve as MLX model shards.

Validate without MLX or model weights

python3 tests/test_llm_workflow.py
bash run_llm_cluster.sh --dry-run --local-ranks 2 --prompt "Hello"

Run on an Apple Silicon Mac

python3 -m pip install -r requirements-llm.txt
bash run_llm_cluster.sh \
  --local-ranks 2 \
  --model mlx-community/Llama-3.2-3B-Instruct-4bit \
  --prompt "Explain pipeline parallelism in three sentences." \
  --max-tokens 128

MLX-LM performs model-aware sharding internally; this repository does not require a separate shard_model.py. For multi-Mac ring and JACCL setup, hostfile examples, latency admission, and platform constraints, open the browser-readable LLM workflow guide.

NumPy LLM Use Case

Explore the numerical core of a decoder-only Transformer without model downloads, GPU dependencies, or Apple-Silicon-only tooling. The compact NumPy example implements token and position embeddings, causal self-attention, a residual MLP block, and autoregressive decoding.

Educational by design: the demo uses deterministic illustration weights, so it is ideal for learning and environment smoke tests—not meaningful text generation. 
python3 -m pip install -r requirements.txt
python3 src/numpy_llm_demo.py \
  --prompt "numpy makes tensor math clear" \
  --max-new-tokens 8
python3 tests/test_numpy_llm_demo.py

See the NumPy LLM use case guide for an LLM-component-to-NumPy-operation mapping and guidance on when to use this local demonstration versus the MLX-LM pipeline.

Known Constraints

ConstraintDescription
Network bottleneckInternet latency is much higher than local interconnects; matrix transfers become communication-bound quickly.
iOS background limitsiOS may suspend background terminal sessions; keep the screen active during runs.
